# ポケモンフレンダ ピックバトル アプリ 仕様書 v0.2

> ポケモンフレンダの「ピック（カード）」に書かれた **ポケモン名 / タイプ / エネルギー値** の3つだけを使って、
> 幼稚園児でも自分ひとりで遊べて、それでいて「ポケモンバトルらしさ」を味わえるデジタル・バトルアプリ。

## 変更履歴

| 版 | 変更内容 |
| --- | --- |
| v0.2 | こうかばつぐんを「2ばい」から「**+20 ダメージ**」に変更／メガシンカ条件を「たいりょく1/2以下」から「**1/3以下**」に変更／**ずかんをデータベース（IndexedDB）で永続管理**する仕様を追加（§7）。所持ピック20枚前提で、チームプリセット・バックアップ機能を追加 |
| v0.1 | 初版 |

## 1. コンセプト

| 項目 | 内容 |
| --- | --- |
| ターゲット | メイン: 4〜6歳（年中〜年長）／サブ: 一緒に遊ぶ保護者・兄姉 |
| プレイ形態 | 1台の端末を2人で交代して使う「ホットシート方式」（対面プレイ） |
| 1バトルの長さ | 2〜7分（3vs3でも約6分） |
| 想定所持ピック数 | 20枚程度（一度登録したらデータベースに残り、次回からは選ぶだけ） |
| 読み書き前提 | **ひらがな・カタカナのみ**（漢字ゼロ）。読めなくても絵と音でわかる |
| 計算前提 | 足し算・引き算ができなくても遊べる（数値の増減はアプリが全部やる） |
| キモ | 「サイコロを振る」「だれをねらうか選ぶ」の2アクションだけ。それ以外は全部自動 |

### 設計の3原則

1. **えらぶのは2つだけ** — 「じぶんのポケモン」と「あいてのポケモン」。あとはサイコロを振るだけ。
2. **まちがえても損しない** — 選択は必ず取り消せる。理不尽な負け筋（0ダメージ・行動不能）は作らない。
3. **かならず盛り上がる山場がある** — ピンチのときにメガシンカで逆転できる。負けている側ほど強くなる設計。

## 3. ゲームルール

### 3.1 バトル準備

1. **人数をえらぶ** — 1vs1 / 2vs2 / 3vs3 の3種類。
2. **チームをえらぶ** — プレイヤー1 → プレイヤー2 の順に、ずかんから人数分のポケモンを選ぶ。
   - **「まえとおなじ」「おきにいりチーム」ボタンでワンタップ編成**できる（毎回選び直す手間をなくす）。
   - 相手の選択画面に移る前に「はい、つぎのひとにわたしてね」という**受け渡し画面**を挟む（覗き見防止 & 交代の合図）。
3. **コイントス** — 画面のコインをタップすると回転アニメーション。表なら先攻、裏なら後攻。
   - 表 = モンスターボールの絵、裏 = ポケモンの足あと の絵。「どっちがでるかな？」と選ばせてから振る形式にして、当事者感を出す。

### 3.2 バトルフィールドの考え方（重要な設計判断）

**チーム全員が最初から場に出る「勢ぞろい方式」**を採用する。控え・交代の概念は持たない。

- 理由: 「攻撃する自分のポケモンと、攻撃対象の相手のポケモンを選ぶ」という要望を素直に実現できる。
- 理由: 「交代」は園児には損得の判断が難しく、ターンを消費する概念自体が理解しにくい。
- 理由: 3体が画面に並んでいる方が、自分の手持ちを見渡せて楽しい。
- 副次効果: 「弱った相手にトドメを刺す」「タイプ相性の良い組み合わせを探す」という、園児にも理解できる戦術が自然に生まれる。

```
   ┌─────────  あいて  ─────────┐
   │  [ピカチュウ]  [リザードン]  [カビゴン]  │   ← タップで攻撃対象を選ぶ
   ├──────────────────────────┤
   │           🎲 サイコロ           │
   ├──────────────────────────┤
   │  [フシギダネ]  [ゲンガー]   [ミミッキュ]  │   ← タップで攻撃するポケモンを選ぶ
   └─────────  じぶん  ─────────┘
```

### 3.3 1ターンの流れ

| # | ステップ | 画面の動き | 誰がやる |
| --- | --- | --- | --- |
| 1 | こうげきするポケモンをえらぶ | 自分の生存ポケモンが光る → タップで選択 | 手番プレイヤー |
| 2 | ねらうポケモンをえらぶ | 相手の生存ポケモンが光る → タップで選択。**「ばつぐん! +20」バッジが自動表示される** | 手番プレイヤー |
| 3 | サイコロをふる | サイコロを大きくタップ（または端末を振る）→ 回転アニメ | 手番プレイヤー |
| 4 | ダメージけいさん | 出目 → ダメージ数値が飛んでいく演出（ばつぐんなら「+20」が追い打ちで表示） | 自動 |
| 5 | たいりょくバーがへる | バーが減るアニメ + 効果音 | 自動 |
| 6 | ひんしはんてい | 0になったら「たおれた！」演出 | 自動 |
| 7 | メガシンカはんてい | 条件を満たしたポケモンがいれば発動演出 | 自動 |
| 8 | こうたい | 「つぎは 〇〇のばん！」→ 端末を渡す | 自動 |

**ステップ1・2はいつでもやり直せる**（サイコロを振るまでは選択解除可能）。

### 3.4 ダメージ計算

```
ダメージ = サイコロの出目の合計 × ダメージばいりつ + ばつぐんボーナス
```

| 要素 | 値 |
| --- | --- |
| サイコロの出目 | 通常 1個（1〜6）／メガシンカ中 2個（2〜12） |
| ダメージばいりつ | **×20（デフォルト「ふつう」）** — 設定で ×10「じっくり」／×30「さくさく」に変更可 |
| ばつぐんボーナス | こうかばつぐんのとき **+20**（固定）／それ以外は +0 |

- 表示は必ず**整数**（10の倍数）になる。小数・端数は絶対に出さない。
- **「いまひとつ」「こうかがない」は実装しない。** 半分にする計算は園児に理解しづらく、0ダメージは「何もできなかった」体験になって楽しくないため。**ボーナスだけがある**設計にする。
- 掛け算ではなく足し算にしたことで、「ばつぐんだと **もう20だけ よけいに** へる」という、園児にも見た目で追える挙動になる。

#### ダメージの実例（ばいりつ ×20 のとき）

| 状況 | 出目 | 計算 | ダメージ |
| --- | --- | --- | --- |
| ふつう | 3 | 3 × 20 | 60 |
| ばつぐん | 3 | 3 × 20 + 20 | 80 |
| メガシンカ中 | 4 + 5 | 9 × 20 | 180 |
| メガシンカ中 + ばつぐん | 4 + 5 | 9 × 20 + 20 | 200 |

#### なぜ ×20 なのか（バランス検証済み）

要望の「出目×10」で 20,000 回シミュレーションした結果、3vs3 が **平均34.9ターン（最大60ターン、約12〜20分）** となり、園児の集中力が持たない長さになる。倍率を上げて再検証した結果が下表（v0.2 のルール＝ばつぐん+20・メガシンカ1/3 で再計測）。

| ばいりつ | 1vs1 | 2vs2 | 3vs3 | 3vs3の想定プレイ時間 |
| --- | --- | --- | --- | --- |
| ×10「じっくり」 | 平均10.8ターン | 平均22.7ターン | 平均34.9ターン（最大60） | 約12〜20分 |
| **×20「ふつう」（推奨）** | **平均5.7ターン** | **平均12.4ターン** | **平均19.3ターン（最大35）** | **約6分** |
| ×30「さくさく」 | 平均3.9ターン | 平均8.8ターン | 平均13.9ターン（最大24） | 約5分 |

> 条件: たいりょく150〜350、こうかばつぐん15.7%、メガシンカ保有率40%、1ターン20秒換算、各20,000試行。
> 再検証は `python3 tools/balance-sim.py` で実行できる。

×20 なら 1vs1 が約1.9分で「もう1回やろう！」を誘発し、3vs3 でも約6分と園児の集中が切れる前に決着する。**倍率は設定画面で変更できる**ようにし、慣れてきたら ×10 でじっくり遊べる余地も残す。

#### ばつぐんボーナス +20 の効き具合（プレイテストで要確認）

+20 は固定値なので、ダメージばいりつによって「効いている感」が変わる。

| ばいりつ | 1回の平均ダメージ | +20 の相対的な重み |
| --- | --- | --- |
| ×10 | 35 | +57%（かなり効く） |
| ×20 | 70 | +29%（ほどよい） |
| ×30 | 105 | +19%（ほぼ誤差） |

ばつぐんの発生率は 15.7% なので、**3vs3 1試合を通じた +20 の総効果は総たいりょくの約4%**にとどまる。狙いどおり「強すぎない」が、逆に**タイプを考えて狙う意味がほとんどなくなる**可能性がある。プレイテストで「ばつぐんを狙う楽しさ」が感じられなければ、**+40 への引き上げ**（総効果 約8%）を検討する。まずは要望どおり +20 で実装する。

### 3.6 メガシンカ

バトル中の山場を作る、逆転のための仕組み。

| 項目 | 内容 |
| --- | --- |
| 発動条件 | **自分のポケモンのたいりょくが 1/3 以下になったとき**、自動で発動 |
| 対象 | ずかん登録時に「メガシンカできる」にチェックを入れたポケモンのみ |
| 回数 | 1バトルにつき、そのポケモン1回だけ（元に戻らない） |
| 効果 | **サイコロが2個になる**（ダメージ期待値が2倍） |
| 演出 | 画面が光る → 専用BGM/効果音 → ポケモンの枠が虹色に変化 → 「メガシンカ！」の大きな文字 |

- 「本当にピンチになってから強くなる」＝発動が終盤に寄るため、**逆転の瞬間がクライマックスになる**。
- 条件が「1/3以下」だけなので、園児が能動的に判断・操作する必要がない。
- たいりょく300のポケモンなら、残り100以下（＝あと1〜2発で倒れる）で発動する。ギリギリ感が出る。
- 判定はダメージ適用の直後に行うため、**同じ攻撃でひんしになった場合はメガシンカしない**（0になったら発動せずに倒れる）。

#### 将来の拡張余地（v0.2 では実装しない）
- ゾロ目で「きゅうしょにあたった！」→ もう1回振れる
- 出目6で +20 ボーナス
- ひんしになった味方の「おうえん」で +10

### 3.7 勝敗

- 相手チームの**全ポケモンがひんし**になったら勝ち。
- 結果画面では「かった！」を大きく祝う一方で、**負けた側にも必ず「〇〇は さいごまで がんばった！」と MVP ポケモンを表示**する（最も多くダメージを与えたポケモン）。園児が泣かないための配慮。
- 「もういっかい」ボタンで同じチーム編成のまま即リマッチできる。

## 4. 幼稚園児向け UX 要件

これは「あったら良い」ではなく**必須要件**として扱う。

| # | 要件 | 詳細 |
| --- | --- | --- |
| U-1 | 文字はすべて ひらがな・カタカナ | 漢字を使わない。フォントは丸ゴシック系、最小 20px 相当 |
| U-2 | タップ領域は最低 64×64 px | 指が太くても押し間違えない |
| U-3 | 読み上げ | 主要メッセージは音声読み上げ（Web Speech API）。文字が読めなくても進行できる |
| U-4 | 常に「つぎ、なにをするか」がわかる | 操作すべき対象は必ず光る・跳ねるアニメーションをつける。それ以外は暗くする |
| U-5 | 待ち時間ゼロの手ざわり | すべてのタップに即座に音とアニメで反応する |
| U-6 | 取り消しできる | サイコロを振るまで選択はやり直せる。「もどる」ボタンを常設 |
| U-7 | 数字は見た目でも伝える | たいりょくは数値 + バー + 色（緑→黄→赤）の3重表現 |
| U-8 | 敗北をやわらげる | 「まけ」より「よくがんばったで賞」を強調。ひんし演出は暗くしすぎない |
| U-9 | 保護者用の入口を分ける | ずかん登録・設定は長押し3秒で入る（園児が誤って設定を壊さない） |
| U-10 | 音のオンオフ | 電車内など無音で遊べるよう、常時アクセスできるミュートボタン |
| U-11 | **一度登録したら二度と入力しない** | ピックはデータベースに永続保存。バトル開始からサイコロを振るまでに文字入力は一切発生しない |

## 6. データモデル（TypeScript）

```ts
/** ポケモンのタイプ（本家18タイプ） */
type PokemonType =
  | 'ノーマル' | 'ほのお' | 'みず' | 'でんき' | 'くさ' | 'こおり'
  | 'かくとう' | 'どく' | 'じめん' | 'ひこう' | 'エスパー' | 'むし'
  | 'いわ' | 'ゴースト' | 'ドラゴン' | 'あく' | 'はがね' | 'フェアリー';

/** ずかんに登録された1枚のピック（データベースの永続エンティティ） */
interface Pick {
  id: string;              // uuid
  name: string;            // ポケモン名（カタカナ）
  type: PokemonType;       // 主タイプ
  energy: number;          // エネルギー値 = 初期たいりょく（150〜350程度）
  canMegaEvolve: boolean;  // メガシンカできるか
  photo?: Blob;            // 実物ピックの写真（任意）
  useCount: number;        // 使用回数（「よくつかう順」の並べ替えに使う）
  createdAt: number;
  updatedAt: number;
}

/** 保存しておいたチーム編成 */
interface TeamPreset {
  id: string;
  name: string;            // 「たろうチーム」など
  pickIds: string[];       // 1〜3件
  updatedAt: number;
}

/** バトル中のポケモンの状態（永続化しない、メモリ上のみ） */
interface BattlePokemon {
  pickId: string;
  name: string;
  type: PokemonType;
  maxHp: number;           // = Pick.energy
  hp: number;              // 0 になったら ひんし
  canMegaEvolve: boolean;
  megaEvolved: boolean;    // メガシンカ済みか
  damageDealt: number;     // MVP 判定用の累計与ダメージ
}

type PlayerId = 'p1' | 'p2';

interface BattleState {
  teams: Record<PlayerId, BattlePokemon[]>;
  turnPlayer: PlayerId;
  turnCount: number;
  phase: 'selectAttacker' | 'selectTarget' | 'rollDice' | 'resolve' | 'handOff' | 'finished';
  selectedAttackerIndex: number | null;
  selectedTargetIndex: number | null;
  lastRoll: number[];      // 直近の出目（メガシンカ中は2要素）
  winner: PlayerId | null;
}

interface Settings {
  damageMultiplier: 10 | 20 | 30;  // デフォルト 20
  soundEnabled: boolean;
  speechEnabled: boolean;
}
```

### 6.1 ダメージ計算関数（仕様の中核）

```ts
const SUPER_EFFECTIVE_BONUS = 20;

function calcDamage(
  attacker: BattlePokemon,
  target: BattlePokemon,
  rolls: number[],
  multiplier: number,
): { damage: number; isSuperEffective: boolean } {
  const diceSum = rolls.reduce((a, b) => a + b, 0);
  const isSuperEffective = TYPE_CHART[attacker.type].includes(target.type);
  const damage = diceSum * multiplier + (isSuperEffective ? SUPER_EFFECTIVE_BONUS : 0);
  return { damage, isSuperEffective };
}
```

- 振るサイコロの数 = `attacker.megaEvolved ? 2 : 1`
- 適用後 `target.hp = Math.max(0, target.hp - damage)`
- `target.hp === 0` → ひんし

### 6.2 メガシンカ判定

```ts
const MEGA_EVOLVE_THRESHOLD = 1 / 3;

function shouldMegaEvolve(p: BattlePokemon): boolean {
  return p.canMegaEvolve
    && !p.megaEvolved
    && p.hp > 0                              // ひんしになったら発動しない
    && p.hp <= p.maxHp * MEGA_EVOLVE_THRESHOLD;
}
```

ダメージ適用の直後に、**攻撃を受けた側の全ポケモン**について判定する。

## 7. データ管理（ずかんデータベース）

一度登録したピックは端末のデータベースに永続保存し、**次回以降は選ぶだけ**にする。

### 7.1 なぜ IndexedDB か

| 選択肢 | 判断 |
| --- | --- |
| localStorage | ✕ 容量が約5MBで、ピックの写真を持つと足りない。文字列しか保存できず、Blob を扱えない |
| **IndexedDB（採用）** | ○ 容量が大きく写真（Blob）をそのまま保存できる。索引付き検索・並べ替えができる。オフラインで動く |
| サーバー上のDB | ✕ v0.2 では不採用。子ども向けアプリとして通信も個人情報も持たない設計を優先。将来 §9 で検討 |

薄いラッパーとして [Dexie.js](https://dexie.org/) を使う（IndexedDB の生 API は冗長で扱いにくいため）。

### 7.2 スキーマ

```ts
// db.ts
import Dexie, { Table } from 'dexie';

class PickBattleDB extends Dexie {
  picks!: Table<Pick, string>;
  teamPresets!: Table<TeamPreset, string>;
  settings!: Table<{ key: string; value: unknown }, string>;
  battleLogs!: Table<BattleLog, number>;

  constructor() {
    super('pickbattle');
    this.version(1).stores({
      picks: 'id, name, type, energy, useCount, updatedAt',
      teamPresets: 'id, updatedAt',
      settings: 'key',
      battleLogs: '++id, finishedAt',
    });
  }
}
export const db = new PickBattleDB();
```

| テーブル | 内容 | 想定件数 |
| --- | --- | --- |
| `picks` | 登録済みピック | 20〜50件 |
| `teamPresets` | おきにいりチーム | 〜10件 |
| `settings` | ダメージばいりつ・音量など | 数件 |
| `battleLogs` | バトル結果の履歴（将来の「きろく」画面用。v0.2 では書き込むだけ） | 増え続けるため直近100件で打ち切り |

**スキーマ変更は必ず `version(n+1)` を足して行う。** 既存の登録データを消さずにアプリを更新できることを保証する（登録し直しは保護者にとって最大の苦痛のため）。

### 7.3 リポジトリ層

UI とドメインは IndexedDB を直接触らず、この interface 越しに使う。将来クラウド同期に差し替える際、この実装を1つ足すだけで済むようにする。

```ts
interface PickRepository {
  list(sort?: 'useCount' | 'name' | 'energy' | 'createdAt'): Promise<Pick[]>;
  get(id: string): Promise<Pick | undefined>;
  save(pick: Pick): Promise<void>;
  remove(id: string): Promise<void>;
  incrementUseCount(ids: string[]): Promise<void>;  // バトル開始時に呼ぶ
}

interface BackupService {
  export(): Promise<Blob>;        // 全テーブルを JSON 化（写真は base64）
  import(file: File): Promise<void>;
}
```

### 7.4 バックアップ（必須）

端末の故障・機種変更・ブラウザのデータ削除で**20枚の登録が消えると、二度と使ってもらえなくなる**。設定画面（S-10）に以下を必ず用意する。

- **「ずかんを かきだす」** — 全データを1つの JSON ファイルとしてダウンロード。
- **「ずかんを よみこむ」** — JSON ファイルを選んで復元。既存データとの重複は `id` で判定し、「上書き」か「追加」を選ばせる。
- 初回登録から一定数（10件）を超えたタイミングで、保護者に一度だけバックアップを促すメッセージを出す。

### 7.5 ピック登録の負担を減らす工夫

20枚の初回登録が最初のハードルになるため、以下を用意する。

- 入力項目は4つだけ（なまえ / タイプ / エネルギー値 / メガシンカ可否）。
- タイプは18色のボタンから選ぶだけ（キーボード入力なし）。
- エネルギー値はテンキー + 「150 / 200 / 250 / 300 / 350」のクイック選択ボタン。
- 「とうろくして つづける」ボタンで、連続登録時に一覧へ戻らない。
- 将来: カメラで撮影して OCR 自動入力（§9）。

## 8. 技術構成

| 項目 | 選定 | 理由 |
| --- | --- | --- |
| 形態 | Web アプリ（PWA） | インストール不要、iPad/スマホ/PC どれでも動く。ホーム画面に追加すればアプリらしく使える |
| フレームワーク | React + TypeScript | 状態管理が素直。型でルールのミスを防ぐ |
| ビルド | Vite | 起動が速く設定が少ない |
| 状態管理 | `useReducer` + Context | バトル進行は状態機械なので reducer と相性が良い |
| データベース | **IndexedDB（Dexie.js）** | ずかん・チームプリセット・設定を永続保存。写真も保存できる |
| 通信 | なし（完全オフライン） | 子ども向けアプリとして、個人情報も通信も持たない設計にする |
| 音声 | Web Audio API + Web Speech API | 効果音と読み上げ |
| テスト | Vitest（+ fake-indexeddb） | ダメージ計算・勝敗判定・メガシンカ条件・DBマイグレーションはユニットテスト必須 |

### 8.1 想定ディレクトリ構成

```
src/
├─ domain/          # ルールの実装（UIとDBから独立、テスト対象）
│  ├─ typeChart.ts
│  ├─ damage.ts
│  ├─ megaEvolution.ts
│  ├─ battleReducer.ts
│  └─ __tests__/
├─ db/              # IndexedDB（Dexie）
│  ├─ db.ts             # スキーマとマイグレーション
│  ├─ pickRepository.ts
│  ├─ backupService.ts
│  └─ __tests__/
├─ screens/         # 画面コンポーネント（S-1〜S-10）
├─ components/      # カード・サイコロ・たいりょくバー等
└─ audio/           # 効果音・読み上げ
```

**ルール（domain）は UI からも DB からも完全に分離する。** バランス調整のたびに UI を触らずに済み、シミュレーションでの再検証も容易になる。
